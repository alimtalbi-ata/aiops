# ACME SAN → Payments — real-runtime customer demo runbook

**Purpose:** Demonstrate the real AIOps2 application workflow using a fully synthetic enterprise incident.  
**Scenario:** `SCN-GOLDEN-PAYMENT-P1` — SAN fabric degradation affecting ACME Payments.  
**Mode:** `DEMO` only.  
**Implementation:** PR #215, branch `integration/real-ai-runtime-demo-20261031`.  
**Safety:** no real SAN/storage/payment changes, no LIVE approval, no SSH/sudo, no production action and no GLPI ticket write.

## 1. What is real, and what is simulated

The demo must be honest about this boundary.

### Real application/runtime behavior

- Portal authenticates a dedicated DEMO operator token and submits a fixed server-owned scenario.
- Portal uses the internal service credential to create a synthetic Incident and canonical DEMO Run through Core APIs.
- Core persists the Incident, Run, idempotency receipts and event timeline in PostgreSQL.
- Core starts the Temporal workflow; the Worker executes the actual stage activities.
- Worker sends the persisted synthetic Evidence set to the Intelligence service.
- Intelligence calls the configured OpenAI-compatible model endpoint for Analyst and independent Critic requests when provider configuration is present.
- Analysis, critique, evidence references, model/provider identity, prompt version, invocation latency and provider-reported token usage are persisted.
- Policy, HITL simulation skip, Temporal execution and verification are represented by actual application events and records.
- Portal Demo Studio reads the canonical Run and displays the same Run ID and event timeline.

### Synthetic scenario inputs / no-effect boundary

- SAN fabric A health, FC error count and Payments context are generated by the synthetic Twin/Simulator adapter.
- No physical SAN, storage array, hypervisor, network switch, payment gateway or business application is contacted or changed.
- DEMO/REPLAY/STORY record HITL as `HITL_SIMULATION_SKIPPED`; this is not a human approval.
- Policy uses `SIMULATE`; no effect receipt, SSH, sudo or command execution is allowed.
- GLPI remains the ITSM system of record, but this demo does not create or update a real GLPI ticket. Ticket/CMDB linkage must remain `UNKNOWN` until an authenticated actor+tenant read contract is qualified.
- A deterministic TEST_PROVIDER is CI evidence only. It must never be described to a customer as a real model invocation.

## 2. Required configuration

Generate unique secrets with `deploy/init-env.sh`. Never copy another server's `.env`.

Required:
- `AIOPS_DEMO_MODE=1` (isolated demo environment only);
- `AIOPS_SYNTHETIC_DEMO_LAUNCH_ENABLED=true`
- a generated `AIOPS_PORTAL_OPERATOR_TOKEN` (at least 32 characters);
- a distinct `AIOPS_PORTAL_READ_TOKEN`;
- `AIOPS_INTERNAL_TOKEN` and database credentials generated per install;
- `LLM_BASE_URL`, `LLM_MODEL`, and `LLM_API_KEY` for an actual OpenAI-compatible provider;
- `AIOPS_DEMO_PROVIDER_KIND=REAL` for a customer demonstration (never use TEST_PROVIDER for a customer claim);
- bounded `LLM_TIMEOUT_SECONDS`, `AIOPS_LLM_MAX_OUTPUT_TOKENS` and `AIOPS_LLM_MAX_REQUEST_BYTES`.

Store `.env` as owner-restricted mode `0600`. Do not print, commit, paste or include tokens/API keys in CI artifacts, screenshots, URLs or support bundles.

If the provider variables are blank or `AIOPS_DEMO_PROVIDER_KIND` is not `REAL`, `tests/synthetic-e2e.sh` refuses the customer rehearsal. Intelligence reports unavailable and the Worker must block the Run. That is a correct fail-closed outcome, not a successful AI demo.

Cost remains `UNKNOWN` unless provider pricing is explicitly versioned. Token totals remain `UNKNOWN` unless the provider returns usage. Do not substitute estimates for provider-reported values.

## 3. Preflight

From the reviewed repository root:

```bash
bash deploy/preflight.sh
docker compose --env-file .env config --quiet
docker compose --env-file .env ps
bash tests/qualification.sh
bash tests/synthetic-e2e.sh
```

Verify that Core, Twin, Evidence, Policy, Worker, Simulator, Portal, Temporal, PostgreSQL and Intelligence are healthy. Intelligence `/ready` should report provider configured. A healthy container alone is not proof that the model endpoint is reachable; a real provider call is required.

## 4. Launch the customer scenario

Open the AIOps2 Portal and use the **Lancer le scénario SAN → Payments** control. Paste the dedicated operator token for this one request. The browser clears the token field and does not persist it.

The server rejects request bodies and accepts no browser-supplied incident, Run, tenant, actor, service, mode, scenario or action. It always launches the fixed `SCN-GOLDEN-PAYMENT-P1` in `DEMO` mode. The optional `Idempotency-Key` makes retries return the same Incident/Run.

For a controlled CLI smoke test, use a shell variable populated without echo and do not enable shell tracing:

```bash
read -rsp 'DEMO operator token: ' DEMO_TOKEN; echo
curl --fail --silent --show-error -X POST http://127.0.0.1:7777/api/demo \
  -H "Authorization: Bearer $DEMO_TOKEN" \
  -H "Idempotency-Key: acme-customer-rehearsal-001"
unset DEMO_TOKEN
```

The expected receipt is HTTP 202 with `state=STARTED`, `mode=DEMO`, `synthetic=true`, a canonical `run_id` and a Temporal `workflow_id`. It must explicitly return `effect_allowed=false` and `live_remediation_authorized=false`.

Open the returned Run in Demo Studio at:

`/demo-studio/run/<RUN_ID>`

## 5. Customer narrative — 7-minute walkthrough

1. **Business context:** ACME Payments depends on its storage and SAN path. The scenario is synthetic and clearly labelled.
2. **Detection:** the simulator records SAN Fabric A degraded (health 0.42) and 184 FC errors/min.
3. **Impact:** Twin context relates the SAN node to the Payments service. Distinguish source-backed edges from assumptions; do not claim a real payment outage.
4. **Analyst:** show ranked hypotheses, supporting/contradicting Evidence IDs, confidence basis, alternatives and missing information.
5. **Critic:** show the independent challenge, unsupported claims, freshness and safety disposition. A Critic rejection must block and leave a durable denial record.
6. **Policy / HITL:** show the Policy decision and reason codes. In DEMO, HITL is explicitly skipped as simulation; never call this human approval.
7. **Verification:** show the synthetic postcondition result, final Run status and event timeline. A simulated resolution is not a production recovery.

## 6. Acceptance checklist

A customer-ready real-model rehearsal requires all of the following on one exact Run ID:

- [ ] Incident is persisted and explicitly marked synthetic.
- [ ] Run is `DEMO`, linked to `SCN-GOLDEN-PAYMENT-P1`, and has a Temporal workflow ID.
- [ ] Twin observations and Evidence records are persisted with source, timestamp, provenance and hashes.
- [ ] Analyst invocation is present with provider/model/prompt version and a real invocation ID.
- [ ] Critic invocation is independent and references the same Evidence set.
- [ ] Analysis and critique records are persisted and visible in the Run timeline.
- [ ] Provider-reported input/output/total tokens are shown when supplied; otherwise usage is UNKNOWN.
- [ ] Latency and retry counts are visible; cost is shown only when pricing is configured and versioned.
- [ ] Policy gate is explicit and a synthetic DEMO cannot obtain LIVE effect authority.
- [ ] HITL event is `HITL_SIMULATION_SKIPPED`, not APPROVED.
- [ ] No effect receipt, executor command, SSH or sudo action exists.
- [ ] Verification evidence is persisted and the terminal state is shown honestly.
- [ ] GLPI ticket/CMDB link is either verified through a tenant-scoped connector or clearly UNKNOWN.
- [ ] The run's exact commit, fixture hash, model/prompt identity and CI run are captured in the rehearsal report.

A Run ending `BLOCKED` or `FAILED` is not a successful customer demonstration. Preserve it as diagnostic evidence; do not relabel it RESOLVED.

## 7. Failure interpretation

| Observation | Correct interpretation / action |
|---|---|
| Portal launch returns 503 disabled | `AIOPS_SYNTHETIC_DEMO_LAUNCH_ENABLED` is false; enable only in the isolated demo environment. |
| Portal launch returns 401 | Operator token is missing/incorrect; never use the internal or viewer token. |
| Run blocks at Analyst | Provider missing, unreachable, unauthorized, timed out or returned an invalid/ungrounded contract. |
| Run blocks at Critic | Critic rejected or could not validate the analysis; inspect durable denial/outbox records. |
| Policy returns BLOCKED | Show reason codes; do not bypass the gate. |
| GLPI shows UNKNOWN / NOT_CONNECTED | Tenant-scoped identity/ticket mapping is not qualified; do not invent ticket numbers. |
| Token usage is UNKNOWN | Provider omitted usage; do not report zero tokens or estimated values as actual. |
| Cost is UNKNOWN | No approved pricing source/version is configured. |

## 9. Current implementation boundary

The Portal's public homepage is an UNKNOWN-first shell and does not perform anonymous Core/Twin reads. The shared viewer token is not a tenant ACL; the bootstrap, Copilot and GLPI ticket fastpaths remain fail-closed until a server-derived actor/tenant authorization contract is implemented.

The synthetic Run status page is intended only for the isolated AIOps2 demo environment. Do not reuse these read paths as a customer multi-tenant authorization design. Before a shared/customer deployment, scope all Run, Evidence, Twin and GLPI reads to a verified identity and tenant, then add cross-tenant denial tests.

The Portal CSP currently allows same-origin scripts and inline scripts for the legacy demo screens. This is a compatibility measure, not the final hardening target. Migrate inline handlers to external same-origin assets or nonce-based CSP before a customer production deployment; no `unsafe-eval` is permitted.
